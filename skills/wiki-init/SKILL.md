# wiki-init

Sets up a complete LLM wiki vault for any project.

This skill has two modes, chosen in Step 0:

**Create from scratch** — when this finishes, the vault has:
- Folder structure adapted to the domain
- `CLAUDE.md` with the project architecture
- `.claude/wiki-conventions.md` with the chosen language, domain-specific tags, and
  (if multi-repo) a repository namespace convention
- `wiki/sync-config.md` so `/wiki-sync` knows which repos to watch and which
  base branch to diff each one against
- `wiki/index.md` (with a "By Repository" section when there are repos) and
  `wiki/log.md` ready to receive pages
- First documentation generated by wiki-forge (optional)

**Connect a remote wiki** — when this finishes, nothing is created locally.
Instead:
- An entry for this project (alias, GitHub repo, path, branch) is saved in a
  personal, per-machine registry at `~/.claude/wiki-registry.json`
- A GitHub access token capable of reading that repo is saved in the same
  registry (reused across aliases when possible) and verified to work
- The user knows to use `/wiki-query` (naming the alias if they have more
  than one project connected) to ask questions from then on

---

## Step 0 — Choose mode

Ask this before anything else. Use `AskUserQuestion`:

- Question: "What do you want to do?"
  Header: "Mode"
  Options:
  - **"Create a new documentation from scratch"** — builds a new wiki in
    this project (normal flow, Step 1 onward).
  - **"Connect a wiki that already exists on GitHub (read-only)"** —
    doesn't create anything here; registers the remote project so it can be
    queried with `/wiki-query`.

**If "Create from scratch"**: continue with Step 1 below, unchanged.

**If "Connect remote"**: go to the "Remote mode" section immediately below
and stop there — do not run Steps 1-6, there is nothing to create locally.

---

## Remote mode — Connect an existing wiki (read-only)

This mode never touches the local filesystem beyond the personal registry
file below. It registers a pointer to a wiki that already lives in a GitHub
repo, so `/wiki-query` can read it later without a local clone. Built for
non-technical users who only need to ask questions, not maintain a wiki.

### R1 — Ask for alias and repo

Ask for the alias using `AskUserQuestion`:

- **"What alias do you want to use to refer to this project? (a short
  word, e.g. 'scorebook')"**
  Header: "Alias" — user types in "Other"

Then ask for the repo URL as a **plain, direct question in the
conversation** — do not use `AskUserQuestion`'s option-list format for this,
there is nothing to choose between, just ask and wait for the answer:

> "What's the URL of the GitHub repository where the wiki lives? (e.g.
> https://github.com/Scorebook-365/wiki)"

Parse the answer into `{ owner, repo }` — e.g.
`https://github.com/Scorebook-365/wiki` → `owner = Scorebook-365`,
`repo = wiki`.

**Do not ask about wiki path or branch — never, these are always fixed:**
- `wiki_path` = `wiki` (the wiki always lives in a `wiki/` folder at the
  root of the repo)
- `branch` = `main` (never query GitHub to detect the repo's actual default
  branch, just use `main`)

### R1b — Get a token, without it ever passing through this chat

These wikis are always private — always assume a token is required, do not
try an unauthenticated request first.

**Golden rule for this whole skill: the token must never enter the
conversation, and must never be read back by this skill's own `Read` tool.**
Not pasted in chat, not echoed in a message, not displayed after being
written. The only things that may ever touch the literal value are (a) the
user's own text editor, and (b) a throwaway shell one-liner that consumes it
and returns nothing but a status code. See R3b and R4 for how.

First, check (without reading the token itself — see R3b for the pattern)
whether the registry already has a non-empty `github_token`:

- **If yes**: ask (`AskUserQuestion`): "Reuse the saved GitHub token, or do
  you need a new one (e.g. if this repo is under a different account or
  organization)?" — Options: "Reuse the saved one", "Use a new one". If
  reusing, skip straight to R2 — nothing else to do here.
- **If no, or the user wants a new one**: continue below.

Tell the user exactly how to create the token, and how to load it without
typing it into the chat. Use a **classic** token, not fine-grained — most
accounts used for this don't have org permissions to mint fine-grained
tokens against someone else's repo, so classic is the one that actually
works:

> "To read that private repo I need a GitHub access token, but never paste
> it here in the chat — you'll load it yourself directly into a file.
> First, generate the token:
> 1. Go to https://github.com/settings/tokens/new
> 2. Type: **Token (classic)**
> 3. Note: any name that helps you recognize it later (e.g. 'wiki-query')
> 4. Expiration: set 90 days — never 'No expiration'
> 5. Scopes: check **`repo`** (there's no narrower option that covers
>    private repos on classic tokens — that's why it matters that this
>    GitHub account only has access to the wiki repo and nothing else
>    sensitive)
> 6. Generate the token and copy it (don't paste it here yet).
>
> Now open this file with a text editor:
> `[registry path — see R3]`
> Find the field `"github_token"` (or `"token"` inside the `[alias]` entry
> if it's a new token for this specific project) and replace the text
> `PASTE_TOKEN_HERE` with the token you copied. Save the file and let me
> know when it's done."

Wait for the user's confirmation before continuing to R2. Do not proceed to
verification (R4) until they say it's done.

### R2 — Check for alias collisions

Read the central registry (see R3 for its path). If the alias already exists
pointing to a **different** repo, warn the user and ask whether to overwrite
it or choose a different alias. If it points to the same repo, treat this as
an update (refresh path/branch/token) rather than a duplicate.

### R3 — Write the registry structure (never the token itself)

The registry is **personal to this machine**, not part of any project repo.
Never place it inside `.claude/` of the current project and never commit it.

Path: `~/.claude/wiki-registry.json`
(`%USERPROFILE%\.claude\wiki-registry.json` on Windows,
`$HOME/.claude/wiki-registry.json` on macOS/Linux). This is the `[registry
path]` referenced in R1b.

```bash
mkdir -p ~/.claude
```

If the file doesn't exist, create it with this shape, using the literal
placeholder string `PASTE_TOKEN_HERE` — **never a real token** — since this
step is done by the skill itself, before the user has edited anything:

```json
{
  "github_token": "PASTE_TOKEN_HERE",
  "wikis": [
    {
      "alias": "scorebook",
      "owner": "Scorebook-365",
      "repo": "wiki",
      "path": "wiki",
      "branch": "main",
      "url": "https://github.com/Scorebook-365/wiki",
      "token": null
    }
  ]
}
```

`github_token` is the default, reused across entries. An entry's own `token`
field is only set (to `PASTE_TOKEN_HERE`, for the user to fill in) when R1b
determined this alias needs a different token than the saved default; leave
it `null` to fall back to `github_token`.

If the file already exists, **do not open it with `Read`** — it may already
contain a real token. Upsert the `alias` entry using a throwaway script
instead (e.g. `python3`/`node`) that loads the JSON, adds or replaces only
the matching object in `wikis`, and writes the file back; have it print
nothing but the list of alias names on success (never the token fields).

After writing, tighten permissions on Mac/Linux (best-effort, skip silently
if unsupported, e.g. Windows via Git Bash):

```bash
chmod 600 ~/.claude/wiki-registry.json 2>/dev/null || true
```

### R3b — Checking for an existing token without reading it

Whenever this skill needs to know *whether* `github_token` (or an entry's
`token`) is set, without needing the value itself (e.g. the check in R1b),
use a script that returns only a boolean-style result:

```bash
python3 -c "
import json, os
p = os.path.expanduser('~/.claude/wiki-registry.json')
d = json.load(open(p)) if os.path.exists(p) else {}
print('HAS_TOKEN' if d.get('github_token') and d['github_token'] != 'PASTE_TOKEN_HERE' else 'NO_TOKEN')
"
```

Never substitute `jq`/`node` output in a way that prints the token value —
only ever print fixed labels (`HAS_TOKEN`/`NO_TOKEN`, `OK`/`FAIL`, an HTTP
status code, a list of aliases).

### R4 — Verify access, without ever seeing the token

Without an MCP server, reading GitHub means calling its REST API directly.
Do this as a single script that reads the token from the file, uses it, and
prints **only the HTTP status code** — never open the registry with `Read`,
never print the token, never let it appear in a command string that gets
shown to the user:

```bash
python3 -c "
import json, os, urllib.request
p = os.path.expanduser('~/.claude/wiki-registry.json')
d = json.load(open(p))
entry = next(w for w in d['wikis'] if w['alias'] == '[alias]')
token = entry.get('token') or d.get('github_token')
req = urllib.request.Request(
    f\"https://api.github.com/repos/{entry['owner']}/{entry['repo']}/contents/{entry['path']}/index.md?ref={entry['branch']}\",
    headers={'Authorization': f'Bearer {token}', 'Accept': 'application/vnd.github.raw'})
try:
    urllib.request.urlopen(req)
    print(200)
except urllib.error.HTTPError as e:
    print(e.code)
"
```

(Any equivalent one-liner in `node`, `jq` + `curl`, or PowerShell's
`Invoke-WebRequest` works the same way — the requirement is just that the
token never leaves that single process as visible output.)

Interpret the printed status code instead of showing a raw error:
- **200**: access confirmed, continue to R6.
- **404**: owner/repo/path/branch is wrong — go back to R1 and re-ask.
- **401**: the token is invalid, expired, or still the `PASTE_TOKEN_HERE`
  placeholder (user hasn't edited the file yet) — go back to R1b.
- **403**: the token is valid but the GitHub account behind it doesn't have
  access to this repo — tell the user to check that this account was added
  as a collaborator (or has org access) to `[owner]/[repo]`, or that the
  `repo` scope was actually checked when the classic token was created.

### R6 — Confirm and explain usage

Report to the user:

```
## Remote wiki connected: [alias]

Repository: [owner]/[repo]  (branch: [branch])
Saved at: ~/.claude/wiki-registry.json

Done. To search this project, use /wiki-query.
```

If this is the **only** entry in the registry, add:
> "Since this is the only wiki connected, you don't need to name it — it's
> used automatically."

If there are **other** entries already, add instead:
> "You have more than one project connected. To ask about this one,
> mention '[alias]' — for example: 'search scorebook for how X works'."

This ends the skill in remote mode — do not run Steps 1-6 below, they only
apply to the "create from scratch" mode.

## Step 3 — Repository details

**If `REPO_COUNT` is "None":** skip to Step 4 with `REPOS = []`.

**If there are repos:** use `AskUserQuestion` with 2 questions:

- **"List each repository, one per line. Format: `name | relative-path | stack | base-branch`. The `base-branch` field is optional — omit it (or leave it empty) to default to `main`. Example: `api | ../my-api | Laravel 11 | main` or `legacy | ../legacy-api | Laravel 8 | master`"**
  Header: "Repositories"
  User types in "Other" with as many lines as needed.

- **"Do you have documents, transcripts, or notes to ingest right now?"**
  Header: "Initial sources"
  Options:
  - "Yes — they're in a folder I'll specify"
  - "Yes — I already put them in raw/"
  - "No — start with an empty vault"

Parse the repo answer line by line. For each line `name | path | stack` or
`name | path | stack | base-branch`, create an object
`{ name, path, stack, base_branch }`. If `base-branch` is missing or empty,
set `base_branch` to `main`. Store as `REPOS`.

Store the sources answer as `HAS_SOURCES`.

## Step 4 — Derive categories and domain tags

Based on `PROJECT_TYPE` and `VAULT_NAME`, generate:

### Wiki categories (subdirectories of `wiki/`)

| Project type | Suggested categories |
|-------------|---------------------|
| SaaS / web app | `architecture/`, `modules/`, `entities/`, `flows/`, `integrations/`, `configuration/` |
| API / backend | `architecture/`, `endpoints/`, `models/`, `integrations/`, `configuration/` |
| Mobile app | `architecture/`, `screens/`, `entities/`, `flows/`, `integrations/` |
| Notes / knowledge | Infer from vault name (courses → `concepts/`, `techniques/`, `resources/`; company → `processes/`, `team/`, `projects/`) |

### Domain area tags

Derive 8-12 business tags based on `VAULT_NAME` and `PROJECT_TYPE`.
Think about the core entities and processes of the project. Examples:

- E-commerce → `products`, `orders`, `payments`, `users`, `inventory`, `shipping`
- EdTech → `courses`, `students`, `instructors`, `payments`, `certificates`, `content`
- Fintech → `transactions`, `accounts`, `users`, `compliance`, `notifications`, `reports`
- Generic SaaS → infer from the project name

Present the derived categories and tags to the user:

```
Based on your project, I'll create these wiki sections:
  [list of categories]

And these domain area tags:
  [list of tags]

Do these look right, or would you like to adjust anything?
```

Use `AskUserQuestion`:
- Question: "Do the categories and domain tags look right?"
- Header: "Structure"
- Options: "Yes, looks good", "Adjust categories", "Adjust tags", "Adjust both"

If adjustment needed, ask a free-text follow-up and apply the changes.

Store the final result as `CATEGORIES` (list of strings) and `DOMAIN_TAGS` (list of strings).

If `REPOS` has 2 or more entries, note internally that Step 5.3 must append the
repository namespace convention section.

### 5.3 — wiki-conventions.md

If `.claude/wiki-conventions.md` already exists, skip this step.

Read `templates/wiki/conventions-template.md` and replace:
- `{{VAULT_NAME}}` → `VAULT_NAME`
- `{{LANGUAGE}}` → `LANGUAGE`

Then append the tags section at the end of the file, writing all labels and descriptions in `LANGUAGE`:

```markdown
## Tag vocabulary

Tags are the most direct retrieval signal. **Only use tags from this list.**
Never invent tags without updating this section first.

Each page carries exactly **1 category tag** + **0-3 area tags** + **0-1 role tag**.

### Category tags (required, exactly 1)

| Tag | When to use |
|-----|-------------|
[One row per category in CATEGORIES — descriptions in LANGUAGE]
| `[category]` | [one-line description] |

### Domain area tags (0-3, only those that apply)

| Tag | Covers |
|-----|--------|
[One row per tag in DOMAIN_TAGS — descriptions in LANGUAGE]
| `[tag]` | [one-line description] |

### Technical role tags (0-1, only if applicable)

| Tag | When to use |
|-----|-------------|
| `core` | Central to the business; high expected query frequency |
| `pattern` | Documents a reusable design pattern |
| `contract` | Defines an interface or agreement between layers |
| `setup` | Configuration or initialization instructions |

### Prohibitions

- **Never** use synonyms of existing tags.
- If a tag seems necessary but isn't in the list: add it here first, then use it.
```

**If `REPOS` has 2 or more entries**, additionally append this section
(translate headings and prose into `LANGUAGE`, keep code/paths verbatim):

```markdown
## Repository namespace (multi-repo)

This vault documents [N] repositories: [list of REPOS names]. To avoid collisions
between entities that repeat across repos (e.g. a `User` model that exists in more
than one Laravel repo), apply this convention whenever an entity name is ambiguous
across repos:

- Prefer subfolders per repo inside the relevant category:
  `entities/[repo-name]/[entity].md` instead of `entities/[entity].md`.
- If a flat structure is preferred instead, prefix the filename with the repo slug:
  `[repo-name]-[entity].md`.
- Only apply this when the same conceptual name exists in **2 or more** repos —
  do not namespace entities that are unique to a single repo.
- The repo slug to use is the `Name` column value from the Repositories table in
  `wiki/sync-config.md`.

### Prohibitions

- **Never** create two pages with the same file name for entities that belong to
  different repos — this is the collision this convention exists to prevent.
```

Write the result to `.claude/wiki-conventions.md`.
